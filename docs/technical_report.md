# 堆喷射检测系统：技术方案与模型创新

## 一、项目背景

### 1.1 什么是内核堆喷射攻击？

内核漏洞利用通常分两步：

1. **触发漏洞**：利用 UAF（Use-After-Free）、Double-Free 或堆溢出等漏洞，释放受害对象的内存槽
2. **堆喷射回收**：大量分配攻击者可控数据的对象，占据刚释放的内存槽，从而劫持控制流

第二步"堆喷射"是漏洞利用的关键环节——没有它，攻击者无法把恶意数据精确放到被释放的位置。

### 1.2 为什么难检测？

堆喷射的本质是"大量正常的内存分配操作"。攻击者用的就是内核正常的分配接口（msgsnd、add_key、sendmsg 等），不触发任何异常。传统的基于漏洞特征或攻击签名的检测方法完全失效。

## 二、数据采集

### 2.1 采集方式

通过 QEMU 启动带有已知漏洞的 Linux 内核（4.15），在 guest 虚拟机内通过 ftrace 追踪 `kmalloc`/`kfree` 事件，同时用 `trace_marker` 标记堆喷射的时间窗口。

### 2.2 数据规模

| 类别 | 说明 | 数量 |
|------|------|------|
| 正常数据（normal） | 8 类负载（空闲/消息队列/密钥/网络/文件系统/fork/内存压力/baseline） | 526 个 run |
| 攻击数据（attack） | 3 个 CVE × 2 个变体（单喷射/组合喷射） | 113 个 run |
| 每个 run | 约 30 秒 trace，~2 万个 kmalloc/kfree 事件 | 6.1 GB 原始数据 |

3 个 CVE 覆盖不同 slab 大小：

| CVE | 漏洞类型 | 目标 slab |
|-----|---------|-----------|
| CVE-2017-11176 | UAF (msg_msg) | kmalloc-2048 |
| CVE-2017-7308 | Double-Free (packet_sock) | kmalloc-256 |
| CVE-2017-2636 | Double-Free (n_hdlc) | kmalloc-8192 |

## 三、检测方法论创新

### 3.1 核心思路：从分配器机制推导判别信号

所有判别信号的根都在 SLUB 分配器的一个性质上：**每个 size class 的空闲链表是 LIFO**。free 一个对象 = 把它压到链表头；下一次同大小的 alloc = 从链表头弹出 → **刚释放的槽会被立刻复用**。攻击者就是靠这个确定性来"把受害对象的槽换成自己的数据"。

从这个机制出发，我们提取了**五维判别信号**：

| 信号 | 攻击中的表现 | 正常中的表现 |
|------|-------------|-------------|
| **单尺寸集中** | 分配高度集中在受害对象所在的 slab | 网络收包/文件系统分配尺寸多样 |
| **单 call_site** | 数千次分配来自同一 syscall 路径 | 不同子系统交替分配 |
| **单核集中** | 喷射绑到单核（CPU-pin） | 正常负载散布在多核 |
| **地址回收** | free→alloc 同地址跨子系统复用 | 同子系统内复用（谁释放谁再分配） |
| **相位顺序** | defrag→free→spray 有时间顺序 | 无特定相位 |

**关键洞察**：单看任何一维都会误报。真正的判别力来自**复合条件**——(高量) ∧ (单尺寸) ∧ (单 call_site) ∧ (单核集中) 同时成立，且按相位顺序出现。这就是为什么要用模型而非单一阈值。

### 3.2 半监督（单类学习）范式

系统仅用正常数据训练，通过重建/偏离误差识别异常。这更符合实际场景——攻击样本稀缺且不断变异，而正常行为可大量采集。

**防泄漏设计**：

- 数据按 **run（采集会话）** 划分 train/val/test，不按序列划分（同一 run 的序列高度重叠，按序列随机划分会泄漏）
- 阈值标定在**验证集正常分数的 p99 分位**，不优化测试集
- test 数据在冻结阈值上**只评估一次**

## 四、模型架构创新

### 4.1 三阶段技术路线

```
阶段 1: 特征增强（schema v3）      → 窗口级，低风险快速验证
    ↓
阶段 2: 事件级 GRU 预测式自监督     → 突破窗口稀释天花板
    ↓
阶段 3: 双轴融合                   → 互补兜底
```

### 4.2 阶段 1：特征增强

#### 问题：窗口稀释

实测 95 个攻击 run 的喷射时长分布：

```
42% < 1ms    55% < 5ms    60% < 10ms    p50 = 2ms
```

当前窗口 100ms，p50 的喷射仅占窗口的 **2%**，98% 是背景噪声。窗口级模型的天花板被窗口粒度锁死。

#### 解决方案：新增 11 维特征

在 100ms 窗口内提取之前被丢弃的判别信号：

| 特征组 | 具体特征 | 说明 |
|--------|---------|------|
| **地址回收**（3 维） | reclaim_count / cross_site_reclaim_count / reclaim_rate | free→alloc 同地址 50ms 内回收次数 |
| **CPU 集中度**（2 维） | cpu_alloc_entropy / top_cpu_alloc_fraction | 攻击 CPU-pin 时熵极低 |
| **对象寿命**（4 维） | lifetime_median / p90 / short_lived / long_lived | 喷射对象"分配不释放" |
| **子窗口突发**（2 维） | burst_dominant_bucket_ratio / burst_dominant_callsite_ratio | 100ms 窗口内找最密集 1ms 子窗口的浓度 |

**实测验证**（spray 窗口 vs 正常窗口）：

```
burst_dominant_callsite_ratio:  spray=1.000  normal=0.395   ← 完美判别
top_cpu_alloc_fraction:         spray=0.991  normal=0.349   ← 完美判别
cpu_alloc_entropy:              spray=0.047  normal=0.219   ← 强判别
```

特征维度从 90 → 101 维（schema v3）。

### 4.3 阶段 2：事件级 GRU 预测式自监督（核心创新）

#### 动机

阶段 1 的根本限制是**窗口聚合稀释了喷射信号**。2ms 的喷射在 100ms 窗口里只占 2%。事件级模型直接在原始事件流上操作，**不存在稀释问题**。

#### Token 设计

将每个内核事件编码为离散 token：

```
token = (操作类型, 尺寸桶, 分配者行为类型, 频率排名, 时间间隔桶)
         2值     12值    4值           4值      4值

词表大小 = 2 × 12 × 4 × 4 × 4 = 1536
```

| 字段 | 含义 | 设计理由 |
|------|------|---------|
| 操作类型 | ALLOC/FREE | 区分分配和释放 |
| 尺寸桶 | 32/64/.../8192/gt | 喷射集中在单一尺寸 |
| 分配者行为类型 | mono/narrow/broad/unknown | 从训练数据自动计算，跨内核泛化 |
| 频率排名 | top5%/p80/p50/罕见 | 罕见 call_site 突然大量出现是异常信号 |
| 时间间隔桶 | <2μs/2-50μs/50-1000μs/>1ms | 喷射间隔极短（<2μs），正常间隔分散 |

**关键设计决策——不使用符号表**：

内核 call_site 是十六进制地址（如 `ffffffff8136ccc1`），理想情况下映射到函数名（如 `kfree`）。但真实环境拿不到符号表（需要 root 权限、KASLR 可能开启）。因此用**数据驱动的行为指纹**替代：

- 行为类型：从训练数据统计每个 call_site 的尺寸分布 → mono（专一尺寸）/narrow/broad
- 频率排名：从训练数据统计全局出现频次 → top5%/p80/p50/罕见

这比地址 hash 更优：不同内核版本的 msg_msg 路径地址不同，但行为画像相同（都是 mono-2048）。

#### 模型架构

```
输入：token 序列 [t1, t2, ..., t128]（覆盖约 0.5-4ms，正好覆盖 p50 喷射 2ms）
  ↓
Embedding: 1536 → 128 维
  ↓
2 层双向 GRU（hidden=128, dropout=0.1）
  ↓
预测头: Linear(128 → 1536) + softmax
  ↓
损失 = next-token 交叉熵（预测第 t+1 个 token 给定前 t 个）
```

参数量约 20 万，GPU 上几分钟训练完。

#### 异常评分：DeepLog top-g 违例法

```
对每个位置 t：模型预测 top-10 候选 token
若真实 token 不在 top-10 → 记一次违例
序列分数 = 违例数 / 序列长度
```

**为什么有效**：模型在正常数据上学到"事件序列是多样化的"——不同 call_site、不同尺寸交替出现。喷射时同一 token 连续重复数百次，模型预测"多样化后继"但真实是"同一个 token"→ 频繁违例。

**实测验证**（3 epochs 训练，200 个序列）：

```
spray 序列违例率:  0.938  ← 128 个位置中 ~120 个违例
normal 序列违例率: 0.028  ← 几乎不违例
```

### 4.4 阶段 3：双轴融合

#### 动机

GRU 和窗口特征模型各有盲区：

| 攻击类型 | GRU（结构轴） | OCSVM（量轴） |
|---------|-------------|-------------|
| 快喷（<1ms） | ✅ 违例率飙升 | ❌ 窗口稀释 |
| 慢喷（>50ms） | ❌ 序列不够长 | ✅ 窗口特征可见 |
| msg_msg 误报 | ✅ 时序区分 | ❌ 同 call_site |

#### 融合方法

```
1. GRU 出序列级违例率，OCSVM 出窗口级异常分
2. 各自按 run 取 max 聚合到 run 级
3. 用验证集正常分数做分位数对齐（→ [0, 1]）
4. 加权组合：score = 0.6 × gru_quantile + 0.4 × ocsvm_quantile
5. 阈值标定在验证集正常 p99
```

## 五、工程创新

### 5.1 多进程预处理

trace2csv / csv2features / trace2tokens 三个预处理脚本支持多进程，默认使用 80% CPU 核（64 核服务器用 51 workers），数据构建时间从数小时降至分钟级。

### 5.2 GPU/CPU 自适应

所有深度学习模型自动检测 GPU：`torch.cuda.is_available()` → CUDA / CPU 自动切换。CPU 路径单线程固定 seed 可复现；GPU 路径高性能训练。

### 5.3 防泄漏数据划分

| 原则 | 实现 |
|------|------|
| run 不跨分区 | `split_run_groups` 按 workload 分层，整 run 划分 |
| scaler 只用 train | `fit_scaler` 只在 train run 上计算 mean/std |
| 阈值只用 val | `threshold_at_fpr` 在 val normal 上标定 p99 |
| test 只评估一次 | 冻结阈值上评分，不回优化 |

### 5.4 可追溯性

每个实验目录记录：输入数据 SHA256、git 版本、Python 版本、配置摘要、split manifest，确保结果可复现。

## 六、模型对比

### 当前模型列表

| 模型 | 类型 | 输入 | 评分方式 |
|------|------|------|---------|
| ocsvm | 窗口特征 | 101 维特征 | -score_samples |
| mlp_ae | 窗口特征 | 101 维特征 | 重建误差 |
| lstm_ae | 序列特征 | 32×101 | 重建误差 |
| **gru** | **事件 token** | **128 token** | **top-g 违例率** |
| **fusion** | **双轴** | **特征 + token** | **分位数融合** |

### 评估指标说明

系统在两个粒度上评估：

- **序列级**：每个 128 事件序列单独判。precision 低是因为攻击 run 有数百个背景序列可能被误判
- **run 级**：每个 run 取最高分判。**这是实际检测效果的体现**——只要有一个 spray 序列被抓到，整个 run 就算检测到
